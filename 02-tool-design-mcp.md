# Domain 2 — Tool Design & MCP Integration

*Tool definitions, MCP servers, external-source handling.*

---

## Confirmed so far

### Handling external / MCP tool output

- **External data ≠ model output** — a tool/MCP result isn't generated by Claude, so you **can't "re-prompt it with feedback"**; correct it deterministically instead.
- **Where & how to enforce → [origin → enforcement layer, D1](01-agentic-architecture-orchestration.md#origin--enforcement-layer)** (canonical): external result → `PostToolUse` normalize/validate before it enters context; deterministic reformat is safe *because* external systems have a stable format contract.
- **Strict tool use** (`strict: true` + `additionalProperties: false`) → schema-valid tool **names & inputs**, but guarantees *shape not truth* → [Conformance ≠ correctness, D4](04-prompt-engineering-structured-output.md).

### MCP tool search & `alwaysLoad`

> **`alwaysLoad` = per-server scalpel; `ENABLE_TOOL_SEARCH` = global policy. Don't cross-wire them.**

- **Tool search** (default on): only tool *names* + *server instructions* load at start; schemas fetched on demand via the `ToolSearch` tool → keeps context lean as servers scale. Same lazy-load pattern as skills; good **server instructions** tell Claude *when* to search.
- **Symptom → fix:** per-turn *latency* while search resolves a constantly-used tool → pre-load it so there's nothing to resolve. Context *bloat* from rarely-used tools → keep them deferred.
- **`alwaysLoad: true`** — per-server field in `.mcp.json`; loads **all** that server's tools upfront **regardless of `ENABLE_TOOL_SEARCH`**, leaving other servers deferred. Use for a **small, every-turn** server. Cost: **blocks startup until that server connects, capped at 5s** (others still connect in background). v2.1.121+. Tool-level equiv: `"anthropic/alwaysLoad": true` in the tool's `_meta`.
- **`ENABLE_TOOL_SEARCH`** (env, global): `unset`/`true` = all deferred · `auto`/`auto:N` = load upfront if within N% (default 10%) of context, else defer · `false` = all upfront, no deferral.
- **Right design:** global deferral (default) **+** targeted `alwaysLoad` on the few constant-use servers.

**Traps:** `ENABLE_TOOL_SEARCH=false` to kill one server's latency (global sledgehammer — loads *all* servers upfront); `alwaysLoad` on the **large, sometimes-used** server (bloats context — it belongs on the small every-turn one); `auto:N` to "target" a server (it's a global threshold, targets nothing). Needs `tool_reference` support — Haiku can't; off by default on GCP Agent Platform / non-first-party proxies.

*(source: [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) — Scale with MCP tool search; Exempt a server from deferral)*

### MCP naming: collisions resolve at the layer where they occur

> **Reserved *server* name → refused at load. Duplicate *tool* name → both load, one wins. Neither ever *merges*.**

| Collision | When caught | Result | Fix |
|---|---|---|---|
| **Server name = reserved built-in** (`workspace`, `claude-in-chrome`, `computer-use`, `Claude Preview`, `Claude Browser`) | **load time** | config → **skipped + warning**; `claude mcp add` → **error** | **rename the server** |
| **Same tool name, two valid servers** | **tool resolution** (both servers load) | Claude **prefers one, ignores the other** (may fail unhelpfully) | server config **`tools` field** to rename/filter |

- **Tools are namespaced** `mcp__<server>__<tool>` — that's the *addressing* scheme, **not** a guarantee of conflict-free coexistence (duplicate tool names still clash → one wins).
- **No merge, ever** — a reserved name is *protected*, not a join point; servers are isolated namespaces.
- **Exam tell:** a custom server named after a native capability (e.g. *screenshot* → `computer-use`; *browser control* → `claude-in-chrome`/`Claude Browser`) = reserved-name collision. Recognize the concept; the 5 exact names are in the row above.

*(source: [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) — reserved server names; duplicate tool-name resolution)*

### MCP config scopes — layered override, whole entry, no merge

> **Scopes resolve like `$PATH` / CSS specificity / git config levels — the highest scope wins the WHOLE entry. A cross-scope name collision is normal (resolved by precedence), never a validation error.**

| Scope | Who sees it | Where it applies | Committed? | Add command |
|---|---|---|---|---|
| **Local** (default) | only you | this project only | no (`~/.claude.json`, keyed by path) | `claude mcp add <name>` |
| **Project** | whole team | this project only | **yes** (`.mcp.json` at repo root) | `claude mcp add --scope project <name>` |
| **User** | only you | all your projects | no (global user config) | `claude mcp add --scope user <name>` |

- **Two independent axes:** *me or the team?* ⟂ *here or everywhere?* (Local = me+here · Project = team+here · User = me+everywhere.)
- **Precedence (high → low):** `Local > Project > User > Plugins > claude.ai connectors`. Scopes match duplicates **by name**; **plugins *and* connectors** match **by endpoint**.
- **Winner's entire entry is used — fields NEVER merge across scopes.** (User `db` with only `env.PGHOST=prod` + project `db` with full command + `PGHOST=staging` → **project entry verbatim, PGHOST=staging**; the user's contribution is discarded, not merged.)
- A server added in Claude Code **beats a claude.ai connector at the same URL** (the connector is shown hidden in `/mcp`).
- Project scope holds no secrets → use `${ENV_VAR}` expansion in `.mcp.json`. Inspect what resolved where with `claude mcp list`.
- **Direction vs skills:** MCP leans *narrow/here* (Local & Project beat User); skills lean *personal* (Personal beats Project). **Opposite directions** — see [D3 skills precedence](03-claude-code-config.md) and [90 direction trap](90-cross-cutting-reflexes.md).

**Traps:** "duplicate name across scopes = config error → both skipped" (**no such behavior** — precedence silently picks one); expecting fields to **merge** across scopes (whole-entry replace only); assuming skills' direction (they're reversed). This is **scope** collision (config layers) — distinct from **tool/server-name** collision at load/resolution time (section above).

*(source: [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) — Scope hierarchy and precedence)*

### Constrained tool design — make invalid states unrepresentable

> **A misused generic tool is fixed by *subtracting* surface (expose only valid ops), never by *adding* tools/access/instructions on top.**

- **Symptom:** a low-level primitive (byte offsets, raw `run_sql`, free-form path) has a huge **failure surface** → the model emits malformed/unrelated/destructive calls.
- **Fix:** replace it with a **high-level, parameterized tool whose every possible call is valid** — `get_clause_by_id(id)` from a pre-parsed index, not `retrieve_clause(offset,len)`; `get_revenue_by_month(month)` (vetted read-only query), not `run_sql(str)`. The bad action becomes **impossible to express**.
- **Free-text box → dropdown.** Constrain inputs to a **validated/closed set** (strong model priors, easy to validate). Avoid inputs needing counting/offset/escaping — a documented failure surface.
- **High-level > low-level:** match how the task is *thought about* ("get clause 7.2"), don't wrap every primitive. Consolidate multi-step ops when it's semantically natural.

**The three anti-patterns (all keep the broken primitive):**
| Wrong move | Why it fails | Reflex |
|---|---|---|
| **Add another tool / broader access** (`raw_file_read`, `describe_schema`) | *adds* surface; misuse still expressible | scope/subtract, don't add |
| **Add a prompt** ("only safe SELECTs") | *guide*, not *enforce* — probabilistic | guarantee needs **code, not a prompt** ([D1](01-agentic-architecture-orchestration.md)) |
| **Add self-check output** (query plan to review) | self-review is unreliable | don't grade your own homework ([90](90-cross-cutting-reflexes.md)) |

*(source: [anthropic.com/engineering/writing-tools-for-agents](https://www.anthropic.com/engineering/writing-tools-for-agents) — defensive tool design; strict data models; high-level vs low-level)*

### MCP primitives — tool vs resource vs prompt

> **Who drives, and how? Model-invoked action = tool · user-attached context = resource (`@`) · user-run template = prompt (`/`).**

| Primitive | Who invokes | How | Think of it as |
|---|---|---|---|
| **Tool** | the **model**, autonomously | model calls it mid-task | an *action* / a search box the agent uses |
| **Resource** | the **user**, explicitly | **`@server:protocol://path`** mention | a *file/document* you attach inline |
| **Prompt** | the **user**, explicitly | **slash command** `/server:prompt` | a saved *prompt template / workflow* |

- **Resource ↔ tool is the crux:** *this one named doc, now* → **resource** (`@docs:file://api/authentication`); *let it fetch whatever it needs* → **tool**. Reference a resource exactly like a local `@file`; type `@` for autocomplete of all servers' resources.
- **Resource = "attach this now," not a startup config.** There is **no `resources` field in `.mcp.json`** that auto-loads a document each session — fabricated mechanism. `.mcp.json` configures *servers*, not documents to inject.

**Traps:** treating a resource like an always-on config load (bloats context; wrong intent — the ask is per-prompt); inventing a `resources:` auto-load field; using a *tool* when the user already knows the exact doc (just `@` it); confusing a *prompt* (user `/command`) with a *tool* (model-invoked).

*(source: [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) — `@` resource mentions; tools/resources/prompts)*

### `tool_choice` — control WHETHER and WHICH tool

> **Two independent questions: *may* the model use a tool, and *which*? `auto`/`none` answer "whether"; `any`/`tool` answer "whether=yes, and pin which."**

| Mode | Meaning | Plain-text reply allowed? |
|---|---|---|
| **`{"type":"auto"}`** | model **decides** per turn: tool *or* text | yes — the only *conditional* mode |
| **`{"type":"any"}`** | must call **some** tool (model picks which) | **no** |
| **`{"type":"tool","name":"X"}`** | must call **that one** named tool | **no** |
| **`{"type":"none"}`** | **cannot** call any tool | text only |

- **Defaults:** `auto` when tools are provided · `none` when none are. `auto` and `none` are opposite ends — *may* call vs *may not*.
- **"Model should decide" → only `auto`.** `any`/`tool` **take the decision away** (force a call); `none` **removes the capability**. An agent that calls tools for live data but answers stable facts directly = **`auto`**.
- **`any`/`tool` prefill the assistant turn** to force a `tool_use` block → the model emits **no natural-language preamble** before the call, even if asked. Want guaranteed structured output with no chatter → `{"type":"tool","name":…}` (works with multiple tools in the array; it pins one).
- **Extended-thinking compatibility: only `auto` and `none`.** Forcing `any`/`tool` **conflicts with thinking** (prefill vs thinking-block-first) → API error. See [D4 extended-thinking sampling lock](04-prompt-engineering-structured-output.md#extended-thinking--sampling-lock).
- **"One turn" = one assistant message = one API round-trip.** A message is a list of content blocks, so a single turn can carry **several `tool_use` blocks** — that's parallel tool use (all issued *before* any result is seen). Multiple *tool calls* ≠ multiple *turns*: turns = round-trips, calls-per-turn can be >1. The model can only batch **independent** calls; if B needs A's result it must go sequentially across turns (a data dependency, not a config knob).
- **`disable_parallel_tool_use` (bool in the `tool_choice` object): mode sets the floor, this flag sets the ceiling.** Default `false` = may emit several calls/turn; `true` caps the turn at **one** call. Combined with mode → `auto`: 0–1 · `any`: exactly 1 · `tool`: exactly 1 of that tool · `none`: **inert** (no calls to cap). Fix "model returned 2 calls, executor handles 1" by *adding* `disable_parallel_tool_use:true` to the existing mode — don't switch modes (that changes the floor too).

**Traps:** `none` for "let the model decide" (that's `auto` — `none` forbids all calls); `any` when you need a *specific* tool (`any` lets the model pick the wrong one → use `tool`); expecting a text explanation before a forced `any`/`tool` call (prefill suppresses it); forcing `any`/`tool` with extended thinking on (rejected — use `auto` + prompt-steer, or drop thinking).

#### "Guarantee the tool" vs "allow same-turn text" is an unsatisfiable pair — the stem's other half decides the answer

> **A hard tool guarantee and a same-turn free-text reply cannot coexist** — forcing (`any`/`tool`) prefills a `tool_use` block, which *structurally* removes the text. So `auto`+prompt gives **behavioral reliability** (model chooses to comply, ~never but not *never* misses); forcing gives a **structural guarantee** (impossible to skip). No mode gives both a guarantee *and* text.**

- **Decision rule — read what the stem asks for *besides* the guarantee:**
  - stem *also* wants same-turn natural-language reasoning/explanation → keep the text channel: **`auto` + explicit prompt instruction** to call the tool. "Guarantee" here can only mean the strongest reliability *compatible with text* — you accept behavioral, not structural.
  - stem is fine with **no** text (just wants the call to be certain) → **force it**: `{"type":"tool","name":…}` (specific) or `{"type":"any"}` (any tool). The text suppression is now a non-issue or a feature.
- **The exam sleight-of-hand:** a stem can say "*guaranteeing* the tool" *and* "optionally explain in natural language on the same turn." Taken literally that's impossible; the intended answer is `auto`+prompt because it's the only branch that keeps **both** goals alive. Don't let the word "guarantee" pull you to `tool` when text is also required — that trades the text away.
- **Why `auto`+prompt isn't a true guarantee:** bare `auto` can (a) call a *different* tool, or (b) reply in **plain text with no tool call at all**. The prompt instruction makes `parse_resume` *behaviorally reliable*, not *structurally guaranteed* — a rare miss remains possible. Only forcing removes that possibility (at the cost of text).

**Traps:** picking `tool` because the stem said "guarantee" while it *also* required same-turn text (forcing kills the text — pick `auto`+prompt); calling `auto`+prompt a "guarantee" (it's behavioral reliability; bare `auto` may skip the tool or run another); assuming the two goals are jointly achievable by *some* clever mode (they aren't — the tension is the whole point). See [90 guarantee=code-not-prompt reflex](90-cross-cutting-reflexes.md) — same behavioral-vs-structural split as constrained tool design above.
